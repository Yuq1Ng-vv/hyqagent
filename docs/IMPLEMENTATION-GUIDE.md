## 一、关键评估

### 1.1 最重要的发现：**不要按sink生成子Agent**

这是你需要的最明确的答案。四个Agent独立搜索了DeepAudit、VulAgent、RepoAudit、VulnSwarm、Skwaq、MAS-Indep等所有主流代码审计系统，**没有任何一个系统按sink生成子Agent**。

原因很简单：

| 粒度 | 500条路径的例子 | 为什么不行 |
|:-----|:-------------|:---------|
| **按sink** | 500个子Agent | 成本灾难。109-Agent真实案例：79%的Agent做无用功。77%的token是缓存读取 |
| **按文件** | 50个子Agent | 仍然太细。每个Agent重新加载上下文，token浪费严重 |
| **按模块/组件** | 5-8个 | ✅ VulnSwarm的做法 |
| **按漏洞类型** | 3-8个 | ✅ VulAgent的做法 |
| **按视角/角色** | 3-4个 | ✅ 最优。MAS-Indep、CodeX-Verify的做法 |

### 1.2 全行业共识

> "Fan out to **find**. Converge before you **verify**. Breadth is for discovery; rigor is for the survivors."

HyqAgent已经有了**CPG**——这是DeepAudit、VulAgent、RepoAudit等系统**没有**的结构性优势。CPG可以以接近零的成本确定性地追踪数据流。用LLM Agent做CPG已经做的事情，是花100倍的钱得到同样的结果。

### 1.3 MAS-Central和MAS-Decent的教训

PLAN.md的研究已经显示：**MAS-Central和MAS-Decent（协调密集型架构）甚至不如单Agent**。你担心的"按sink生成子Agent"恰恰是这两种失败架构的典型模式——增加协调复杂度但不增加真正独立的视角。

## 二、实现风险清单

### 按阻塞程度排序

| 优先级 | 问题 | 阻塞程度 | 预计额外投入 | 对策 |
|:------|:-----|:--------|:----------|:-----|
| **P0** | 跨文件调用图（反射/DI/动态import） | 卡住1-2周 | +10-15天 | 先支持无反射/无DI的Python项目；Spring DI暂缓 |
| **P0** | 测试基准不存在 | 持续性阻塞 | 持续投入 | 手动构造50-100个已知漏洞的WebGoat/DVWA/VulnPy回归集 |
| **P1** | 框架传播器（Propagator）被低估 | 初版1-2周 | +7天/框架 | 从Flask一种框架开始，只做request→sink的直接路径 |
| **P1** | LLM验证的可复现性仅17-25% | 设计层面问题 | +3-5天 | temperature=0 + 多次交叉验证 + L1确定性验证权重更高 |
| **P2** | tree-sitter语法边界 | 渐进消耗 | +3-5天 | 锁定版本，防御性编程，查询外加重试循环 |
| **P2** | Prompt缓存TTL与长任务不匹配 | 增加成本 | +1-2天 | 缓存断点放在系统prompt上(1h TTL)，不放在对话历史上 |
| **P2** | LLM的"自信幻觉"不可见 | 质量风险 | 持续关注 | 每个发现必须有CPG可验证的代码证据 |
| **P3** | Taint配置维护 | 量大但不复杂 | 持续 | 社区贡献+自动从文档推断source/sink |

### 2.1 最可能让你卡住一整天的具体问题

1. **tree-sitter Python binding segfault** — `tree-sitter==0.23.1`在复杂查询时触发空指针解引用。CI中约7-9%失败率。Workaround：查询外围包重试循环。

2. **Joern Lambda数据流断裂** — 这是已知bug，且"不在任何roadmap上"。Lambda内引用外部变量时数据流丢失。

3. **动态import解析失败** — GitLab Orbit的实践：无法解析的import直接丢弃调用边。React/Next.js等现代框架大量使用动态import。

4. **SQLite WAL checkpoint饥饿** — 持续写入下WAL文件可以无限增长（几十GB）。一个未关闭的读事务就能阻止checkpoint。

5. **LLM过度自信** — 无论对错都表达>85%的高置信度。会流畅地描述不存在的漏洞。

### 2.2 基准数据集的残酷现实

| 数据集 | 真实质量 |
|:-------|:--------|
| BigVul | 标签准确率仅**54.3%**，18.9% train-test泄露 |
| PrimeVul | StarCoder2从BigVul的F1=68.26%暴跌到**F1=3.09%** |
| Juliet | 已被LLM记忆（等同于泄题） |

**没有任何专门针对Web漏洞的高质量标注真实项目基准。** 你需要手动构造。

## 三、多Agent架构决策

### 3.1 明确答案：HyqAgent当前不需要多Agent架构

四个Agent的独立研究得出了一致结论：

**单Agent + 多视角prompt（Multi-Perspective Single Agent）是HyqAgent第一阶段的最优架构。**

| 架构 | 成本 | 召回率 | 复杂度 | 适合场景 |
|:-----|:-----|:------|:------|:--------|
| 单Agent单视角 | 1x | 50.8% | 极低 | MVP、CI/CD快速门禁 |
| **单Agent多视角** | 3x | **~60%** | 低 | ✅ 推荐：HyqAgent第一阶段 |
| 多Agent(3个独立) | 2.5x | 64.2% | 中 | 深度审计、发布前审查 |
| 多Agent(5+协调) | 5x+ | ≤单Agent | 高 | ❌ 研究证明劣于单Agent |

### 3.2 单Agent多视角的具体做法

```
同一段代码，用不同的prompt调3次LLM：

Pass 1: Security Auditor视角
  "你是安全审计员。找出这段代码中所有可被利用的漏洞。"

Pass 2: Attacker视角  
  "你是攻击者。审计员说这段代码是安全的。证明他们错了。
   尝试绕过所有防护措施。即使有消毒，如何绕过？"

Pass 3: Completeness Critic视角
  "审计员和攻击者都看过了。你作为完整性审查员，
   他们漏了什么？哪些漏洞类型没被检查？哪些假设可能是错的？"
```

对比多Agent：三视角用**同一个Agent、不同prompt、隔离的上下文**，而非三个独立的Agent进程。这捕获了MAS-Indep多样性红利（+13.4pp）的大部分，但没有多Agent的协调开销。

CodeX-Verify的关键数据：多样性来源于**不同的视角**，而非不同的Agent进程。4个Agent之间的相关性仅ρ=0.05-0.25——但这是由不同的prompt设计驱动的，而不是由不同的Agent实例驱动的。

### 3.3 如果未来需要多Agent，唯一合理的模式是：

**一个额外的Critic/Verifier Agent**（对抗性，如果可能使用不同模型家族），审查主Agent的发现，有严格的"用代码证据推翻"的授权。

- 这是单Agent→多Agent的**唯一ROI为正的增量**
- 提供真正的独立性（不同的prompt、不同的上下文窗口）
- 直接解决LLM的最大问题（自信幻觉）
- 其他一切（MAS-Central、MAS-Decent、按sink生成子Agent）基于当前证据都是ROI为负的

## 四、推荐的架构方案

### 4.1 HyqAgent Phase 2 的最优设计

```
Phase 1: CPG-First Filtering (确定性, 零LLM成本)
  └─ CPG识别所有sink，追踪污点流
  └─ 按风险评分排序
  └─ 过滤到top-N高风险路径

Phase 2: Triage筛选 (单Agent, 轻量级, ~$2)
  └─ 对所有500条路径做快速评分
  └─ 高风险(~30%) → Phase 3深度分析
  └─ 中风险 → Phase 3简化分析
  └─ 低风险(明确误报) → 自动归档

Phase 3: 多视角LLM分析 (单Agent, 3 Passes, ~$5)
  └─ Pass 1: Security Auditor
  └─ Pass 2: Attacker
  └─ Pass 3: Completeness Critic
  └─ 合并和去重发现

Phase 4: 对抗性验证 (便宜模型, ~$0.50)
  └─ Haiku级别验证器检查代码证据
  └─ 拒绝无代码证据支持的发现
  └─ 仅确认发现进入深度分析

Phase 5: 深度分析 (强模型, 仅3-5个幸存者, ~$2)
  └─ Opus/Sonnet级别深度推理
  └─ 完整可利用性分析 + PoC构造
```

### 4.2 为什么这个设计优于多Agent

1. **CPG做了其他系统用Agent做的事情** — DeepAudit的Recon+Analysis Agent做的事情，CPG确定性地以零成本完成
2. **3个视角捕获了大部分多样性红利** — MAS-Indep的+13.4pp主要来自不同的分析策略，而非不同的Agent进程
3. **Triage节省了大量成本** — $2的轻量筛选如果排除60%的低风险路径，净节省$3+
4. **深度分析只用在幸存者上** — "广度用于发现，严格用于幸存者"，单这一条就节省了约70%的成本
5. **无协调开销** — 不需要跨Agent通信、去重、共享状态管理

### 4.3 与多Agent的对比

| 维度 | 单Agent多视角(推荐) | 3 Agent独立(MAS-Indep) | 5 Agent协作(MAS-Central) |
|:-----|:------------------|:---------------------|:---------------------|
| 成本 | ~$8-10/项目 | $12-15/项目 | $15-20/项目 |
| 延迟 | ~8min(串行3次) | ~4min(并行) | ~6min |
| 预估召回率 | ~60% | ~64% | ≤50.8% |
| 工程复杂度 | 低 | 中 | 高 |
| 幻觉控制 | 3视角交叉 | 3独立判断 | 协调器成瓶颈 |
| 维护成本 | 低 | 中 | 高 |

## 五、MVP范围建议

### 5.1 第一版：验证核心假设

**语言**：**只做Python**（一种语言，做到极致）

**漏洞类型**：**先做5种**
1. 命令注入 — 模式清晰，CPG数据流可追踪
2. SQL注入 — 经典且高影响，验证CPG污点追踪
3. 反序列化漏洞 (pickle/yaml.unsafe_load) — Python特有，高影响
4. 路径遍历 — 简单但常见
5. 硬编码密钥 — 纯模式匹配，不需要CPG

**框架**：**先做Flask**（一种框架）

**核心验证路径（7周）**：

| 周 | 做什么 | 验证什么 |
|:--|:-----|:--------|
| 1-2 | Baseline：Bandit+Semgrep跑10个已知CVE项目 | SAST工具的TP/FP基准 |
| 3-4 | CPG-only：Joern生成CPG，写3-5个CPGQL查询 | CPG是否比AST模式匹配FP更低 |
| 5-6 | CPG+LLM：CPG切片→LLM分类 | LLM是否能显著提升precision |
| 7 | 三方对比报告 | 决定是否继续投入LLM |

**如果precision没有显著提升，LLM可能不值得。** 多个开发者从LLM退回regex/AST的教训：如果CPG已经解决了FP问题，LLM增加的延迟和成本可能不合理。

### 5.2 不要在第一版做的事

- ❌ Web UI / Dashboard
- ❌ 多语言支持
- ❌ 多Agent架构
- ❌ CI/CD集成
- ❌ 用户认证 / 多租户
- ❌ "AI Agent自主决策" — 先证明检测质量
- ❌ 超过5种漏洞类型
- ❌ 认证绕过 / 业务逻辑 / 竞态条件检测 — 学术界仍在攻克

### 5.3 第一版最简CLI

```bash
hyqagent scan ./myapp --lang python --framework flask
# 输出: JSON报告，包含漏洞类型、位置、置信度、证据链
```

## 六、技术选型踩坑清单

### 6.1 tree-sitter

| 问题 | 严重程度 | 对策 |
|:-----|:--------|:-----|
| py-tree-sitter segfault (v0.23.1) | 高 | 锁定版本，查询外加retry loop |
| Query对象静默失败返回零匹配 | 中 | CI中7-9%失败率，加重试 |
| ABI版本不匹配 | 中 | 从master分支安装以获取兼容性修复 |
| 跨文件分析需自建图 | N/A(预期内) | Joern CPG处理跨文件 |

### 6.2 LLM

| 问题 | 严重程度 | 对策 |
|:-----|:--------|:-----|
| 过度自信(>85%置信度，无论对错) | 高 | 每个发现必须有CPG可验证的代码证据 |
| 验证可复现性仅17-25% | 高 | temperature=0，关键判断多次交叉验证 |
| Prompt缓存5min TTL | 中 | 缓存断点放在系统prompt(1h)，不在对话历史 |
| 代码片段>50个示例后准确率下降 | 中 | 10-50个示例/prompt是甜点区间 |
| Precision远比Recall重要 | 关键 | 开发者信任是脆弱的，噪音中迅速崩溃 |

### 6.3 SQLite

| 问题 | 严重程度 | 对策 |
|:-----|:--------|:-----|
| WAL checkpoint饥饿 | 高(静默) | 监控WAL文件大小，定期PRAGMA wal_checkpoint |
| 并发写入瓶颈(>20 Agent) | 低(HyqAgent单Agent) | 不适用，但需知道上限 |
| 事件日志增长 | 中 | 大artifact外存到JSON文件 |

### 6.4 Joern

| 问题 | 严重程度 | 对策 |
|:-----|:--------|:-----|
| Lambda数据流断裂 | 中 | 已知bug，不在roadmap |
| 语言前端成熟度不均 | 中 | Python前端相对成熟 |
| 查询版本脆弱性 | 中 | 锁定Joern版本 |

## 总结

### 回答你的两个问题

**Q1: 开始实现会遇到哪些问题？**

最大的三个：跨文件调用图（反射/DI/动态import）会让你卡1-2周；没有可用的Web漏洞基准数据集让你不知道自己做对了没有；LLM的"自信幻觉"（流畅地描述不存在的漏洞）会严重破坏信任。

**Q2: 应该有子Agent并行分析吗？**

**明确答案：不应该。** 业界没有任何成熟的代码审计系统按sink生成子Agent。109-Agent的真实案例显示79%的Agent在做无用功。你的CPG已经以零成本提供了其他系统需要用Agent来实现的数据流追踪能力。建议的Phase 2架构是：**单Agent + 三视角(Critic) + 轻量级Triage + 深度分析仅用于幸存者**。这个设计捕获了多Agent多样性红利的大部分，但没有多Agent的协调开销和成本爆炸。

### 最关键的一句话

> **先用CPG证明你比Bandit/Semgrep的误报率更低——这是你最容易赢的地方。在数据上证明优势后，再引入LLM。LLM的角色是"切片分类器"而非"漏洞发现者"——CPG发现潜在路径，LLM判断是否为真实漏洞。Precision是唯一重要的指标——宁可漏掉一些漏洞，也不要报告不存在的漏洞。后者会摧毁开发者信任，而信任无法恢复。**
